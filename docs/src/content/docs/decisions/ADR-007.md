**Date**: 2026-07-04
**Status**: Decided

## Context

Every onboarding is validated by the platform's own conformance suite. The suite's verdict on `main` is not always green: it also checks facts outside the studio's control (sibling repo contracts, deploy branches), so "the suite passes" is the wrong acceptance bar for a single change.

## Decision

The gate is a baseline diff. Before mutating, the studio runs the suite on `main` (the baseline). After mutating and re-running the generators, it runs the suite again. The change may not introduce any failure `main` does not already have. On a failed gate, every touched file is restored byte-identical and the branch is discarded. Generators (`gen-dashboards`, `gen-homepage-repos`, the docs `gen-projects`) are re-run rather than their outputs hand-edited.

## Rationale

- Diffing against the baseline isolates the change's own effect: an onboarding is not blocked by a pre-existing failure it did not cause, and cannot hide a new failure behind one.
- Byte-identical rollback means a rejected onboarding leaves no trace; the checkout is exactly the repo the next action starts from.
- Re-running the generators instead of editing their outputs keeps registry-derived files (dashboards, homepage, docs index) unable to drift from the registry, which is the property the generators exist to guarantee.

## Alternatives considered and rejected

- **Require a fully green suite after the change**: couples every onboarding to failures outside its blast radius; a broken sibling repo would freeze all onboarding.
- **Hand-edit generated outputs as part of the change**: produces files that claim to be generated but are not; the first regeneration silently reverts the edit.
