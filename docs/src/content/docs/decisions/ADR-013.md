**Date**: 2026-09-08
**Status**: Decided

## Context

The platform's [ADR-045](https://github.com/VFPT-VODAFONE-FOUNDRY/adf-platform/blob/main/docs/src/content/docs/decisions/ADR-045.md) made brokering data: an install declares `defaultBrokers` on its deploy branch, and the identity grant splices whatever is declared into every realm it renders. Its consequences call the migration small — "each install adds the declaration describing what it already does" — and note that a realm already rendered "carries what it was rendered with until that app is reconciled".

Nothing reconciled it. `onboard_identity` raises `AlreadyExistsError` for an app whose realm block exists; `reconcile_app` re-renders the five skeleton files and, by INT-SKELETON-001's disjointness, never touches a grant file; `grant_drift` (INT-GRANT-007) is a read on purpose. An install that granted six realms and then declared a broker, or named a login theme (INT-GRANT-009), had a studio that could report every realm out of date and repair none. The hand edit was the only path, and a hand-applied provider on each realm — under the very alias the install then declared — was its result.

Two earlier defects bound the shape of any repair. Reconcile once rewrote a skeleton file wholesale and deleted a live generator's Role and RoleBinding out from under it (foundry-platform#100). Normalising the fleet against the template once proposed deleting an admitted operator from two live realms, caught only by a semantic guard (INT-GRANT-007's rationale).

## Decision

**A separate verb, `reconcile_identity`, not a mode on the grant.** Onboarding grants a capability and states `grant.issued`; a re-render grants nothing. It rides the reconcile family's branch (`reconcile/<app>-identity`), commit (`fix(identity): reconcile <app> realm`) and pull-request shape, on the same gate-validate-rollback path.

**Documents are replaced, never files.** The render's two documents — the `keycloak-realm-<app>` ConfigMap and the `keycloak-<app>-provision` Job — replace the document of the same kind and name wherever the folder carries it (`replace_document`), the concern file first. The file around them is byte-identical: the database grant's Jobs, the `gen-keycloak-<app>` generator that mints the app's own credential, its ServiceAccount and RBAC. The credential wiring — the `keycloak-<app>` Secret, the `<app>` client, the host, the issuer the app already points at — is therefore unchanged by construction.

**Users are carried, not compared.** The re-rendered ConfigMap carries the template's own users block (the realm admin is platform-owned and is re-rendered like the rest) followed by every entry the branch's realm listed under any other username, verbatim, comments included. This is the same line INT-GRANT-007 draws for the read, applied to the write: the realm's user list is its access allowlist, people are admitted by hand by design, and a render keyed on the app name cannot know them. Everything else in the realm is the template's. A provider a team wants for itself belongs in the app's own chart, applied as its realm-scoped admin (ADR-045 section 2), which this never reads and the Job applies no-delete around; a provider someone hand-applied to the platform's copy is exactly what a re-render supersedes.

**One renderer, so a reconciled realm is indistinguishable from one granted today.** The re-render calls `render_identity_blocks` with the same arguments onboarding would, and the documents it writes are byte-identical to a fresh onboarding's for the same declaration. There is no second template and no reconcile-only variant.

**A current realm is refused before any branch is prepared.** When the branch already carries what the template renders, the verb raises `AlreadyExistsError` (409 over REST; a typed refusal over MCP, per ADR-012) and prepares nothing — the settings write's no-op rule (INT-GRANT-006). A sweep over every realm therefore opens a pull request only where something changed.

**The pull request says what changed and why, and the callback stays the operator's.** The body names each declared alias as newly declared, already brokered (its rendering converges the provider Keycloak holds under that alias), or no longer declared (the grant stops converging it; providers apply no-delete, so removing it from Keycloak is the realm admin's act), and whether the login theme moved. Registering a broker's callback with its IdP is outside git and is named in the checklist only for an alias the realm did not previously carry: the alias fixes the callback path, so an alias already brokered was registered when it first was.

## Consequences

- The ADR-045 migration is now a studio act per realm: declare on the branch, then `reconcile_identity` each app, register the new callback where the checklist says so.
- The "hand-applied provider of the same alias" case converges rather than duplicates: the alias is the key on both the realm and the Job env, and `IMPORT_MANAGED_IDENTITYPROVIDER=no-delete` updates in place.
- A broker removed from `defaultBrokers` leaves Keycloak's copy standing. That is INT-GRANT-005's guarantee working as designed, and the pull request says so rather than implying a deletion that does not happen.
- INT-GRANT-010 holds the whole contract; `grant_drift` reads in sync immediately after a reconcile, which is the check that the two halves agree.

## Alternatives considered

**A `rerender` flag on `onboard_identity`.** Rejected: it would make one verb both grant and repair, publish `grant.issued` for a realm that already existed, and put the append and the replace behind one switch. The repo already names repair `reconcile`.

**Replace the whole `config.yaml` and `jobs.yaml`.** Rejected on foundry-platform#100: those files carry the database grant and the credential generator, and a file-level write is how a live generator lost its RBAC.

**Compare users semantically and re-emit them.** Rejected: re-emission loses the comments and layout someone wrote for a person, and the reconciled realm would no longer be byte-identical to a fresh onboarding's even when nobody was admitted. Carrying the entries as text keeps both properties.

**Carry hand-applied identity providers too.** Rejected: after the grant a realm's providers are the team's *in the team's chart* (ADR-045 section 2), not in the platform's ConfigMap; carrying them there would freeze the very hand edit the declaration exists to replace, and `TEAM_OWNED_REALM_KEYS` already draws the line at `users`.
