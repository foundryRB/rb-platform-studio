**Date**: 2026-07-04
**Status**: Decided

## Context

The studio is a management surface over `foundryRB/rb-platform`, a repository that moves on its own: the maintainer merges onboarding PRs, edits manifests, and evolves the conformance suite independently of any studio release. The pod needs that content available to read and to mutate.

## Decision

The pod clones `foundryRB/rb-platform` onto a PersistentVolumeClaim at first start and polls upstream (`STUDIO_PLATFORM_POLL_SECONDS`) to stay at head. The image carries application code only; platform content is never baked into it. The content's version history, audit trail, and merge semantics are git itself.

## Rationale

- A management surface over a moving repo would bake staleness in: any snapshot taken at image build is outdated by the first merge that follows it.
- App image releases must not couple to content pushes; the studio ships on its own cadence, and the platform repo changes on the maintainer's.
- The PVC keeps the checkout warm across pod restarts; the poll keeps reads honest between restarts.

## Alternatives considered and rejected

- **Bake the platform repo into the image at CI**: correct only for content frozen at release time; here every merged onboarding PR would immediately outdate the running image, and keeping it fresh would demand cross-repo rebuild machinery for no gain.
- **Read the repo over the GitHub API per request**: pushes latency and rate limits into every read and leaves no working tree for the conformance suite and generators to run against.
