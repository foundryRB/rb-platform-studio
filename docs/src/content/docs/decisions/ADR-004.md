## Context

Agents need the studio's capabilities: read the registry, run conformance, onboard apps and databases. The studio already exposes these capabilities through inbound ports consumed by the REST adapter and the SPA.

## Decision

The MCP server is a third inbound adapter, mounted at `/mcp` on the same application using streamable HTTP. Tools mirror the inbound ports one-to-one. The onboarding tools exist in every composition; the PR surface (`list_onboarding_prs`, `refresh_platform`) exists only where the composition manages the clone. Serialization reuses the HTTP DTO mappers, so the OpenAPI contract stays the studio's single serialization surface.

## Rationale

- One shared core means every MCP onboarding goes through the identical gate-validate-rollback path as the SPA and REST; trust calibration is enforced in one place.
- Deriving the tool list from the capability wiring keeps the deployed and local instances honest about what they expose, with zero mode branches.
- Mirroring the DTO mappers mechanically means the MCP surface can never drift from the HTTP one; there is no parallel shape to maintain.

## Alternatives considered and rejected

- **A separate MCP service** in front of the REST API: a second system with its own auth, deployment, and drift surface, wrapping capabilities the hexagon already exposes as ports.
- **MCP-specific response shapes**: a second serialization surface that drifts from the OpenAPI contract as soon as either evolves alone.
