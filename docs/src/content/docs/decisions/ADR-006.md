**Status**: Decided

## Context

A complete onboarding touches two repos with different owners: the platform repo (the studio's datastore) and the app's own repo, whose `deploy` branch and contract files are team-owned. It also involves credentials that must never enter git.

## Decision

The studio mutates only its own datastore. The app repo's scaffolding ships as the `onboard-app` MCP prompt: a runbook, parametrized with live registry facts, that the consumer's agent executes in the repo it owns (the client-executes idiom). Cross-repo access stays read-only. Secrets stay imperative by design: the studio never holds or applies credentials; PR bodies at most list the secret templates to fulfill.

## Rationale

- The app repo's `deploy` branch is team-owned; a studio writing it would need a credential into every consumer's repo and would blur who owns what it wrote.
- The runbook-as-prompt keeps the studio the single source of the procedure while the executing hands, and the accountability, stay with the repo's owner.
- A studio that never holds credentials cannot leak them, and the platform's existing out-of-band secret flow stays the only path a real value travels.

## Alternatives considered and rejected

- **The studio opens PRs against consumer app repos too**: requires a cross-repo write credential per consumer, and puts the studio's name on changes the team must own and maintain.
- **The studio applies secrets it is given**: turns the studio into a credential intermediary; any such convenience path becomes the leak surface, and the imperative flow already exists.
