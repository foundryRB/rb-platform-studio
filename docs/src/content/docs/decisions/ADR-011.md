**Date**: 2026-07-27
**Status**: Decided

## Context

Two of an app's Secrets exist only because a grant's generate-if-absent Job mints them in the cluster: the Keycloak realm credential (`keycloak-<app>`) and the Postgres role password (`pg-app-<app>`). The demand side is the app chart's own `k8s/values.yaml`, which names them as `existingSecret` values; the provide side is the install branch's `teams/<app>/` folder, which must carry `gen-keycloak-<app>` or `gen-pg-app-<app>`.

A chart naming one with no grant to mint it schedules a pod that waits forever on a Secret nothing will ever create. Nothing goes red on the way there: the values parse, the templates render, the release publishes, and the failure surfaces days later as `CreateContainerConfigError` on the cluster. `task-api` shipped exactly that and sat broken for 12+ hours.

The check needs both halves, and neither side's own CI has them. In the app's CI the chart is checked out but the platform repo is not, and the app runner holds no credential to fetch it (the platform repo is private; the org token is packages-only). In platform CI the install branches are readable but no app repo is checked out. So the rule existed as an executable check that ran only in a local maintainer pre-flight - the one place a human was already looking.

The studio is the one place both halves are already in reach: it serves the install's deploy branch and reads app repos over the repo host through the `AppRepoSource` port (ADR-010).

## Decision

The install conformance suite carries a per-app credential row, `install/credentials::demand-grant[<app>]` (INT-GRANT-004). It reads the app repo's `k8s/values.yaml` off the default branch, collects every `existingSecret` leaf, and holds each platform-minted credential named there to the matching generator among the `metadata.name` values in `teams/<app>/`. An unreadable chart reports skipped, never passed.

**The row is advisory to the onboarding gate.** It is reported and never refused on, which is a deliberate exception to ADR-007's baseline diff. The reason is an ordering deadlock: the grant the row asks for is rendered into `teams/<app>/`, which `onboard_app` must create first, while `onboard_identity` and `onboard_database` refuse an app the manifest does not yet carry. A gate that admitted on this row would refuse every app whose chart already reads a platform-minted Secret - the app onboarding refused for a missing grant, the grant's onboarding refused for a missing app - with no order that resolves it.

Advisory does not mean invisible. A failing row surfaces at three places:

- **`run_conformance`** reports it as an ordinary failing row.
- **The onboarding PR body** carries an Advisory section naming the row, why the gate did not refuse on it, and which grant to run after the merge.
- **The app's status chain** carries it as its own `credentials` link, positioned immediately before `probe`. It is outside the stage derivation, so an app in this state reads `promoted` with `credentials` as its first non-ok link: the chain names the cause instead of blaming the edge.

## Rationale

- **The gap is only visible where both halves are.** Running the cross-check server-side is not a new coupling: the studio already reads app repos for the delivery and promotion rows (ADR-010), under the same one-way, read-only, unreadable-reports-skipped discipline. This row reads one more file under the same rules.
- **Advisory beats a deadlock, and beats nothing.** The alternative to the exemption is either a gate that cannot admit ordinary apps, or no check at all. Reporting without refusing keeps the finding while leaving the onboarding sequence workable.
- **The chart's values are the readable, conventional half.** The fleet's charts carry every credential name as an `existingSecret` that templates then reference through `.Values`, so one file read per app is the whole demand side, with no template fan-out and no extra token scope beyond what the existing app-repo rows already require.
- **The status chain is where it gets acted on.** A gate rejection interrupts someone mid-task; this finding usually arrives later, when the chart adds a demand after onboarding - a push to the app repo that no studio call observes. The status link is the surface that a delivery run is already polling.

## Consequences

A chart naming a credential in a template rather than in values escapes this row. That shape is already outside the app-repo contract, and holding the conventional half is what turns the silent never-ready state into a finding.

The row is derivable, not alarming: nothing polls it on its own. An app that breaks this way after onboarding stays broken until someone reads `run_conformance` or `app_status`. Closing that gap is a separate concern (a scheduled run, or the console surfacing it) and not part of this decision.
