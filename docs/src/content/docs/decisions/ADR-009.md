## Context

The platform's ADR-032 delivers the platform the way it delivers every app: `main` holds the canonical source (the platform chart, the seed, the conformance suite, the docs), no cluster reconciles it, and each install is one orphan `deploy-<install>` branch holding four things: `foundry.yaml` (the install manifest: `parts` and `output` app entries with name, display, icon, and an optional `mcp` flag), `values.yaml` (the zone and install facts), `root/` (the app-of-apps with the chart pin), and `teams/<app>/` folders split per concern (`namespace.yaml`, `gateway.yaml`, `rbac.yaml`, `application.yaml`, `routes.yaml`, plus grant files where onboarded). Every manifest-derived view (dashboards, homepage bookmarks, the docs Projects index) is rendered from the manifest by the platform chart on sync; the registry generators do not exist. The earlier decision records here name `main` (ADR-001, ADR-002) or "the default branch" (ADR-008) as the branch of record because, before ADR-032, the one install's state lived there.

## Decision

The studio serves exactly one install, and the install's deploy branch is its datastore.

- **Branch = install.** `STUDIO_DEPLOY_BRANCH` (no default; PR-mode fails closed if unset) names the branch; the managed clone parks on it, reads come from it, onboarding branches fork from its head (the fetch-with-prune re-onboarding guard of INT-GATE-003 unchanged), pull requests base against it, and the lifecycle fast path of ADR-008 direct-commits to it. Nothing the studio does touches `main`; the one exception is reading the platform's `intent.yaml` (the conformance claims surface), which lives on `main` and is read from the clone's ref.
- **Registry semantics become manifest semantics.** An onboarding adds one entry to `foundry.yaml` under its role (`parts` for apps the Foundry depends on, `output` - the default - for apps it built and runs), carrying name, display, and icon. An MCP endpoint is the entry's `mcp: true` flag; the URL derives from the zone in `values.yaml` and is stored nowhere.
- **The team artifact is a folder.** The whole folder is rendered from the studio's canonical templates keyed on the install's own facts, the skeleton (namespace, Gateway, RBAC, Application, docs route) from `team_skeleton` and the capability grants from `database_grant` / `identity_grant`, landing split by kind into the concern files (ServiceAccount in `serviceaccount.yaml`, the grant's RBAC in `grant-rbac.yaml`, Jobs in `jobs.yaml`, the realm ConfigMap in `config.yaml`). A grant's files and the skeleton's files are disjoint sets, because reconcile re-renders every skeleton file wholesale: while the grants routed their Role and RoleBinding into the skeleton's own `rbac.yaml`, reconciling an app deleted the RBAC out from under its live generator Job (foundry-platform#100). No part is copied from a donor app (this supersedes the initial skeleton-mirror; INT-SKELETON-001, a string-mirror could not produce this install's `deploy-<install>` targetRevision and silently carried a donor's stray blocks).
- **No generator step.** Views render from the manifest inside the platform chart, so a gated change writes only authored artifacts and the generator-drift class is structurally impossible (INT-GEN-001 pins this from the studio's side).
- **The gate validates the candidate working tree.** The platform's own conformance suite reads committed `deploy-*` refs and cannot see uncommitted candidate state, so the studio runs its own install conformance checks (the manifest-teams bijection, entry shape, derived MCP endpoints, ArgoCD Application wiring, database-grant isolation) over the working tree, keeping ADR-007's baseline-diff semantics and the byte-identical rollback of INT-GATE-001.

## Rationale

- **One studio per install is ADR-032's own shape**: onboarding is an act against a specific install, targeted at its branch; a studio that wrote to `main` would mutate a branch no cluster reconciles.
- **The gate must judge what the PR ships.** Only the working tree holds the candidate; adapting the per-install checks to it keeps the gate honest without inventing a commit-then-test dance on the control-plane repo.
- **Deriving the MCP URL keeps one authored fact.** The zone already lives in `values.yaml`; storing per-app URLs would be a second copy that drifts.

## Alternatives considered and rejected

- **Committing the candidate to a throwaway branch so the platform suite can see it**: the suite enumerates `deploy-*` branches, so the candidate branch would either be invisible or masquerade as a second install; and a failed gate would leave commits to clean up where the rollback contract wants bytes restored.
- **Running the platform suite from a `main` checkout against the working tree**: the suite's fixtures read git refs by design (orphan branches need no working tree); redirecting them at an uncommitted tree means patching the platform repo from the studio, upside down.
- **Keeping a per-app `mcp_url` in the manifest entry**: rejected by ADR-032's manifest shape; the flag plus the zone is sufficient and cannot drift.
