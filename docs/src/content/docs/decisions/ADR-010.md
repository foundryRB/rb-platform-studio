**Date**: 2026-07-21
**Status**: Decided

## Context

An app was onboarded with the whole install conformance suite green while it could not possibly ship. Its `.github/workflows/build.yml` was a hand-rolled lint/test workflow that never called the shared reusable workflow, so CI published no image and no chart to GHCR; and the install's `deploy-<install>` branch did not exist in the app repo, so the rendered ArgoCD Application had nothing to reconcile. Both rules already exist as executable checks on the platform side (`test_repo_conformance`: INT-FOUNDRY-013 for the CI caller, INT-FOUNDRY-020 for the deploy branch), but neither is reachable when the gate needs them: the in-CI audit runs only inside repos that already call the shared workflow (circular), and the platform-side pytest run skips repos not checked out as sibling clones. The gate the onboarding actually passes through (ADR-007/009) saw neither.

The two legs live in the app repo, which is team-owned (ADR-006): the studio must not clone or mutate it, and the deploy branch legitimately does not exist at onboarding time - the onboarding runbook stands it up only after the PR merges and CI first publishes the chart, so a gate that refused its absence would deadlock every greenfield onboarding.

## Decision

The install conformance suite carries two per-app delivery rows, read off the repo host over the `AppRepoSource` port (the GitHub REST and raw APIs; no clone, no mutation):

- **`install/delivery::ci-caller[<app>]`** (INT-FOUNDRY-013): the app repo's `.github/workflows/build.yml`, read off its default branch, must call the shared reusable workflow as `uses: <owner>/<ci repo>/.github/workflows/build.yml@...` (the repository carrying it is the organisation's to name, `ci` or a prefixed name; the row pins the owner and the workflow path). The app-repo contract requires the caller before onboarding, so a readable repo whose `build.yml` is hand-rolled, or absent from the default branch's file listing, fails; an unreadable repo (absent, or not granted to the studio's token) and a `build.yml` read that goes unanswered report skipped.
- **`install/delivery::deploy-branch[<app>]`** (INT-FOUNDRY-020): the branch the rendered Application reconciles (`deploy-<install>`) must carry `dev/values.yaml`, `dev/Chart.yaml`, `prod/values.yaml`, and `prod/Chart.yaml`. A branch that exists without the full env config fails; a branch that cannot be read (not stood up yet, host unreachable) reports skipped.

The gate semantics stay ADR-007's baseline diff, which gives the rows their teeth: a brand-new app has no baseline rows, so any failed delivery row on an onboarding is a new failure and the PR is refused and rolled back. Fail wrong, name absent:

- **Fail what is verifiably wrong.** A hand-rolled `build.yml` or a deploy branch missing its env config blocks the onboarding.
- **Name what is absent.** A skipped delivery row is a named warning: the onboarding PR body carries a Delivery pipeline section listing every `install/delivery::` row for the app with its outcome, and states that a skipped row is pending verification, not a pass. The onboarding runbook's verify step requires every delivery row PASSED from `run_conformance` before the app counts as shipping.
- **Skipped never reads as passed.** Repo-host reads ride a short TTL cache so a gate's baseline and candidate runs judge the same snapshot, and a composition without a wired `AppRepoSource` (local runs, tests) reports the rows skipped.

## Rationale

- **The gate must see what decides whether the app can ship.** The manifest entry and team folder are necessary but not sufficient; the CI caller and the deploy branch are the two team-side legs without which the delivery pipeline delivers nothing, silently.
- **Hard-blocking absence would reorder greenfield onboarding.** The deploy branch is created after the merge by design (the chart it pins must first be published by CI, which the onboarding does not gate on), so absence is the legitimate declares-it-will-ship state; only present-and-wrong proves a defect.
- **A silent skip reproduces the original failure.** The suite that admitted the unshippable app reported green because the unverifiable legs were invisible; naming every skipped delivery row in the PR body and requiring them passed post-onboarding keeps "not yet verified" distinguishable from "verified" at every surface.

## Alternatives considered and rejected

- **Hard-block both legs (onboarding as the last act of first release)**: catches everything at the gate but deadlocks the documented sequence - the deploy branch pins a chart CI publishes only after the app repo is live, and requiring it before the onboarding PR inverts the runbook for no defect caught that fail-wrong does not also catch.
- **Warnings only (never fail)**: keeps ordering untouched but re-admits the hand-rolled `build.yml`: the one defect in the incident that was verifiably wrong at onboarding time would again ship green-with-footnotes.
- **A separate post-onboarding verification step**: adds a second gate the operator must remember to run; the suite already reruns on every `run_conformance` and every later gated change, so the rows land there instead, and the runbook's verify step is the required act.
