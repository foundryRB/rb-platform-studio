**Date**: 2026-07-31
**Status**: Decided

## Context

`create_app_repo` creates an org repository and seeds it with the walking-skeleton scaffold — the whole REF-Foundry app-repo contract rendered from the studio's canonical templates, so the repo is green in its own CI from the first push. It then stands up the install's `deploy-<install>` branch.

All three writes went through the git-data API: `POST git/trees` with the file contents inline, `POST git/commits` with no parents, `POST git/refs` to create the branch. That shape is correct for a deploy branch — an orphan branch on a repository that already has history — and it is what `onboard_app` has always used successfully.

It cannot work on a repository the same call just created. The repository was created with `auto_init: false`, so it had zero commits, and **the git-data API answers 409 ("Git Repository is empty") on a repository with no commits**. The tree write was the very first thing `create_app_repo` did after creating the repo, so on a greenfield it failed every time. The 22 rendered files never left memory.

The failure was invisible in three separate places, which is why it survived:

1. The use case raised `PrFailedError` naming the half-built repo, correctly — but the Foundry Console, its only caller, swallowed every exception from this path by design (a studio that is down should degrade to a bare repo, not block a delivery).
2. Every test faked the writer with a method that returned `True` unconditionally, so no test could distinguish a working write path from a broken one.
3. The repository that was left behind looks exactly like a healthy new app from the outside: right name, right description, right visibility. The Console's own `.delivery/` writes then created `main` through the **Contents** API — which does work on an empty repository — so the repo even had a default branch and commits on it.

`proxiverso` was established this way. It carried its delivery scratch and none of the contract, with the absence due to surface at build-and-ship, several phases later.

## Decision

**Auto-init is part of the port contract, not an implementation detail.** `create_repository` creates the repository carrying an initial commit, because a repository with no commits cannot be written through the git-data API at all. `AppRepoWriter.create_repository` says so in its docstring: its postcondition is `seed_branch`'s precondition.

**Seeding and orphaning are separate methods with opposite preconditions.** `seed_branch` updates a ref that already exists, parented on its head; `create_orphan_branch` creates a ref that does not, with no parents. A freshly created repo's default branch needs the first; a deploy branch needs the second. Getting them backwards is what shipped, so they no longer share a method.

The seed's commit **parents the auto-init head** and the ref update is an ordinary `PATCH` — never a force. A force capability on this writer would eventually be pointed at a live deploy branch. The tree carries no `base_tree`, so the branch ends up holding exactly the rendered files and nothing of the initial commit but the parent link. The cost is one throwaway commit in the history, which semantic-release ignores.

**Repository and scaffold are atomic.** A seed that cannot land deletes the repository it created (`delete_repository`) and the refusal says so. A rollback that is itself refused — a token without `delete_repo` — must not read like one that worked: the message names the surviving empty repository and the hand it needs.

**The deploy branch is the deliberate exception.** It is derived state a later `onboard_app` can stand up, so its failure is logged and the scaffold still counts.

## Consequences

The write credential now wants `delete_repo` in addition to contents read/write. Without it the rollback leg degrades honestly rather than silently: the repository survives, and the caller is told so in the refusal.

Scaffolded repos carry two commits on `main` — GitHub's `Initial commit`, then `feat: walking-skeleton scaffold (rendered by platform-studio)`. semantic-release cuts `1.0.0` from the second, which is the version the deploy branch is already pinned at.

The test fakes now model the host's preconditions rather than answering `True`: a repo has commits only once created with auto-init, orphan creation needs history and an absent ref, seeding needs a ref that is there. Wiring a leg wrongly turns a test red instead of a repository. `tests/integration/test_github_app_writer.py` pins the adapter's own calls — most directly that `auto_init` is `true`, the flag whose absence caused this.

**A refusal now names its own error class on the wire.** MCP flattens an exception to `str(e)` (mcp's lowlevel `_make_error_result`, via FastMCP's `Error executing tool <name>: <e>`), so the type is lost in transit while the REST door next door maps that same type to a status code. A caller left with only prose cannot reliably tell `AlreadyExistsError` — adopt the repo, entirely ordinary — from `PrFailedError` — the scaffold failed, refuse. `create_app_repo` therefore refuses through `_typed_refusal`, which leads with `type(exc).__name__` and then states the reason, and `tests/integration/test_mcp_api.py` pins both refusals at the protocol level. This is a workaround for the door, not a design: `foundry-console#42` moves the Console's writes to the internal REST port, where the status code carries the type natively.

This ADR covers the studio's half. The Console's swallow was a defect of its own and is fixed there: its MCP gateway never inspected the JSON-RPC `error` envelope, so a failing tool call returned an empty result instead of raising, and no `try/except` in the Console could have caught it.

## Alternatives considered

**Bootstrap through the Contents API.** `PUT /repos/{owner}/{repo}/contents/{path}` does work on an empty repository — it is what the Console's `.delivery/` writes use, and GitHub documents it as the workaround. But it writes one file per call and one commit per file: 22 calls and 22 commits for this scaffold. Rejected on both counts.

**Keep `auto_init: false` and force-update after a Contents-API bootstrap.** Gets to a single clean commit, but needs a force capability on the writer to collapse the bootstrap commit away. Rejected: the single-commit history is not worth a method that can overwrite a branch.

**Leave the half-built repo and let the caller repair it.** This is what the code did, and the message even told the operator to seed it by hand or delete and retry. Nobody read it, because the only caller could not surface it. Making the operation atomic removes the need for every caller to handle partial failure correctly.
